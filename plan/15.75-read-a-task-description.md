# Milestone 15.75: Read a task's description and comments ✓

[← all milestones](../plan.md)

Delivered, then extended on request: the pane shows the task's **comments**
under its description, with who wrote each one. That was not in the plan below
— §4's "out of scope" did not exclude it because it did not occur to anyone —
so it is written up in [§9](#9-comments) rather than threaded through the
sections it postdates.

Seven deliberate deviations from the plan below.

1. **The fetch is asked for from `draw`, not from `handle_key_event`.** §5 put
   it beside the config write-through, on the settled-burst gate. The gate is
   right and it is the same gate; the *place* was wrong. A key is not the only
   thing that moves the cursor off a row — `settle_table` can rebuild the
   table out from under it, and that happens in `draw`. Asking from
   `handle_key_event` left the pane holding the previous task's text until the
   next keystroke. `draw` aims the pane unconditionally and fetches behind
   `!input_pending`, which covers both and keeps a burst to one request.
2. **`FocusedPane` gained a third variant.** §2 routed `Mode::Description` to
   `FocusedPane::Task` by analogy with gantt mode. That drew *both* panes with
   the focused border, because the chart lives inside the task pane's frame
   and the description has a frame of its own. The question "where do my keys
   go" now has three answers because there are three panes that can hold them.
3. **`o` is bound in description mode — and `handle_action` had to be told
   too.** §3 said `o` "stays the escape hatch" and left it at that. It is
   bound in task mode rather than in `Mode::Any`, so from the new mode it did
   nothing while the hint bar advertised it. (The bar drops a hint whose
   action has no key in the current mode, so the symptom was a silently
   missing hint rather than a dead key.) Binding it was only half the fix:
   `Action::Open`'s arm resolves the URL by matching on the mode, so a
   binding alone still opened nothing. Two places, not one.
4. **`v` is advertised in task mode's hint bar and help overlay.** The plan
   listed `description_groups` for the new mode and stopped there, which left
   the way *in* documented nowhere. This is the one place the "byte-identical
   when closed" rule in §9 is deliberately broken: `task-mode-200` and the
   task-mode help snapshots now carry `v description`. At 80 and 120 the hint
   bar sheds it from the right, so no existing hint was displaced.
5. **The client answers with the text alone, and the cache keys on the
   *record's* timestamp.** §4 had `get_task_description` return
   `TaskDescription { notes, modified_at }`, with `modified_at` fetched
   alongside the notes so the entry could record which version of the task it
   belonged to. That is a fetch loop waiting to happen: the two reads can
   disagree — a task modified between the list request and this one — and a
   mismatch no later read can resolve is a cache that misses on every frame,
   which is a thread and a request per frame. Keying on the value the loaded
   record already carries, captured when the request goes out, cannot
   disagree with itself. `DESCRIPTION_OPT_FIELDS` is `"gid,notes"`, the method
   returns `String`, and `TaskDescription` does not exist. §4's argument for a
   non-nullable return still holds and is now carried by the `String`.
6. **The pane lays prose out itself rather than handing it to
   `wrap_to_width`.** §6 said "`text::wrap_to_width` does the wrapping… the
   pane needs no wrapping of its own". That was wrong twice over, and both
   were visible the moment a real description went in:
   - **A single `\n` is a paragraph break, not a line break.** Asana's editor
     makes a new block every time Enter is pressed and `notes` joins those
     with one newline, so taking a newline at face value ran every paragraph
     into the one before it. `layout` drops the source's blank lines and
     inserts its own between blocks, which also means `\n` and `\n\n` read
     identically — the text lays out the same however it was typed.
   - **A wrapped list item needs a hanging indent.** Flush continuations turn
     `- carrier pickup window confirmed in writing` into two items, the second
     of which is the word "writing". Each item now hangs by the width of its
     own marker, so `9.` and `10.` in one list line up with their own text,
     and consecutive items are not spaced apart — a list is one block, so the
     blank goes before it and after it, not through it.

   The notes under "Implementation" said hanging indents were "guessing at
   structure" that plain `notes` does not carry. A bullet and a number *are*
   that structure, written by the person who typed them; declining to read
   them is its own guess, and the worse one.
7. **`line 0/0` is shown for an empty description, and a `description-short`
   snapshot was added.** The count is how a reader tells "this task has
   nothing written on it" from "the pane has not caught up yet", so the empty
   state keeps its chip rather than dropping it with the text.

Notes from implementation:

- the compiler worklist §2 predicted was exactly five arms: `Mode::label`,
  `focused_pane`, `help_visible`, `Theme::mode_color`, and the help overlay's
  dispatch. Nothing was silently missed, and `allows_any_fallback` needed no
  arm, as predicted
- the snapshots caught both of the real bugs — the double-focused border and a
  fixture whose description sat on a row the cursor never starts on. Neither
  would have failed a unit test
- the property test — no laid-out line may be wider than the pane, at every
  width from 4 to 60 — found two overflows a hand-written case would not have:
  a marker whose width was taken off the continuation lines but not the first,
  and a marker as wide as the pane itself. The renderer does not clip, so
  either would have corrupted the frame
- two of the integration tests only pass as two batches rather than one. That
  is the design working: inside a single burst the fetch is still out when
  `ctrl-d` arrives, and there is no text to scroll yet

Goal:

- draw a task's description in a pane to the right of the task table — the space
  the Gantt chart would otherwise occupy — and give it a bind mode of its own so
  a long description can be scrolled a half page at a time
- **the table keeps the cursor.** `j` and `k` still move from row to row with the
  pane open, and the pane follows the cursor. Reading down a list of tasks is the
  flow this is for; the pane is a second column of the same review, not a
  destination you navigate into
- fetch the text **lazily, for the row under the cursor**, and only once per
  task per session. The task list request is not touched: a description is
  unbounded text, and fetching one for every task in every selected project to
  show three of them would make every project load pay for it
- **behaviour must not change when the pane is closed.** It is closed by
  default; with it closed, every rendered frame is byte-identical to today's.

## Target design

The task pane's region splits in two. The table keeps the left, the description
takes the right, and each keeps its own frame — unlike the chart, which shares
the table's interior because it is drawn per row. A description is a block of
wrapped text and has nothing to say row by row, so it gets a pane.

```
 TUISANA  ▸ 1 project ▸ 4 tasks                                                    description
┌─ Projects ───────────────────────────────────────────────── 3 shown · 1 selected · 2 hidden ┐
│  ● ★ Northwind BTX 4412                                                                     │
└─────────────────────────────────────────────────────────────────────────────────────────────┘
┏━ Tasks ━━━━━━━━━━━━━━━━━━━━━━━━━ 4 tasks · row 2 ┓┌─ Description ──────────────── line 1/18 ┐
┃   Task                           │ Assignee      ┃│ Hand the packaged release candidate     │
┃▌Northwind BTX 4412 ──────────────────────────────┃│ over to the study team for the 4412     │
┃   Study Kit Design ──────────────────────────────┃│ run. Everything below has to be true    │
┃   Review shipment requirement…   │ Morgan Ellis  ┃│ before it ships:                        │
┃▍● Ship release candidate to t…   │ Alex Chen     ┃│                                         │
┃   ↳ Confirm carrier pickup win…  │ —             ┃│ - labels printed from the current       │
┃   Close out packaging vendor …   │ Alex Chen     ┃│   template, not last quarter's          │
┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┛└───────────────────────── +11 more lines ┘
 DESCRIPTION  ctrl-d/ctrl-u scroll  v close  o open in Asana                 r refresh  q quit
```

Reading it:

- **The pane does not name the task.** The cursor row is two cells to its left
  and already says which task this is; printing the name again would spend the
  one line the title has on something the eye has just read. The title is the
  noun, like `Tasks` and `Projects`.
- `line 1/18` is where the scroll is: the first visible line and how many the
  text wrapped to. It is a count of what the pane is showing, so it rides the
  top border on the right, like every other pane's counts.
- `+11 more lines` rides the *bottom* border, the way the chart's legend does,
  and only when there is more below. It is the same phrasing `src/ui/notice.rs`
  already uses for a clipped message.
- The table reflowed because its region got narrower, and the existing
  horizontal scroll is what reaches a column the narrower budget clipped — no
  different from turning the chart on.

The four states that are not text:

```
┌─ Description ───────────────────────────┐   ┌─ Description ───────────────── line 0/0 ┐
│                                         │   │                                         │
│                loading…                 │   │            (no description)             │
│                                         │   │                                         │
└─────────────────────────────────────────┘   └─────────────────────────────────────────┘

┌─ Description ───────────────────────────┐   ┌─ Description ───────────────────────────┐
│                                         │   │                                         │
│        no task under the cursor         │   │      could not load: 404 not found      │
│                                         │   │                                         │
└─────────────────────────────────────────┘   └─────────────────────────────────────────┘
```

All four go through `chrome::render_pane_message`, which is what the task pane
already uses to say "loading" and "no tasks" — so an empty description looks
like every other empty pane in the app rather than like a bug.

Design rules carried forward from [Milestone 11.5](11.5-visual-redesign.md) and
[Milestone 12](12-gantt-chart-view.md):

- **The right of the task pane holds the chart *or* the description, never
  both.** This is the same rule the top pane already lives by: it holds the
  project list or the filter panel, and which one is a visibility flag rather
  than the mode. Squeezing columns, a chart, and a description into one pane
  would leave all three too narrow to read. Opening the description suppresses
  the chart for as long as it is open and touches none of the chart's state, so
  closing it brings the chart back exactly as it was.
- **Fixed chrome height.** The pane is a horizontal split of a region that
  already exists. Nothing above or below it moves, and no body line is spent.
- **Show deviations, not defaults.** One `description` settings chip, and only
  while the pane is open.
- **Every binding is configurable.** The new mode takes its keys from the keymap
  like every other mode; the hint bar and the help overlay resolve their key
  names from it.
- **Never rely on colour alone.** Nothing here is colour-coded: the pane is
  prose. The `mono` variant needs no special case beyond the border glyphs it
  already owns.

Explicitly out of scope, to be a later milestone if wanted: **editing** a
description (this milestone is `notes` read-only, and an editor for multi-line
text is a different problem from the one-line `TextEditState` every field runs
on today); fetching `html_notes` to recover formatting plain `notes` has
thrown away — bold, links, and real list nesting (what §6's `layout` reads is
the markers a person typed into the plain text, which is a different and much
cheaper thing); full-page
`ctrl-f`/`ctrl-b` and `home`/`end` jumps inside the pane; searching within a
description; and showing subtask descriptions inline.

## 1. The key, and why it is not `r`

`r` is `refresh`, bound in `Mode::Any`. A `Mode::Task` binding would shadow it,
and `KeyMap::action_for` tries `(mode, key)` before `(Any, key)` — so the mode
that most wants to reload its own rows would be the one mode with no key to do
it. `v` is the key instead:

- `v` is bound in `Mode::Project` only (`toggle_hidden_group`), and nowhere in
  `Mode::Any`, so taking it for task mode and description mode displaces nothing
- it reads as "view", which is what the pane is, and it keeps `r` meaning
  refresh in the one view where refreshing matters most
- uppercase `R` was the other candidate — [Milestone 15 §4](15-create-and-delete-tasks-and-sections.md)
  made uppercase a mode-scoped namespace, so it would work. It is not used here
  because the uppercase namespace means something in this app: lowercase acts on
  the task, uppercase on the structure around it. A reading pane is neither

## 2. The mode

`Mode::Description`, in `src/config/mod.rs` beside `Mode::Gantt`, with the same
relationship to `Mode::Task`: the same pane, the same rows, the same cursor and
selection, different keys. The plumbing is one arm each, and exhaustive matching
makes it a compiler worklist:

- `Mode::label` → `"description"`
- `Mode::allows_any_fallback` → needs no arm. It excludes only the modes that
  type text, and this one does not, so the globals keep working: `j`/`k` move
  the cursor, `t`/`f`/`p` switch panes, `r` refreshes, `q` quits, `?` helps
- `focused_pane` → `FocusedPane::Task` (`src/ui/runtime.rs`)
- `help_visible` → `app.tasks.help_details_visible()` (`src/ui/runtime.rs`)
- `Theme::mode_color` → `Color::Cyan`, the same as `Mode::Gantt` and for the
  same reason: another read-only view over the rows the table is already showing
- `handle_action`'s pane dispatch needs no change — the mode is not
  `Project`/`ProjectSearch`, so actions already route to `self.tasks`

`App::set_description_mode` follows `set_gantt_mode`: `prepare_mode_switch`,
make the task pane visible, make the pane visible, close the filter panel if it
is open. It additionally asks for the cursor row's text (§5).

## 3. Actions and default bindings

| mode | key | command | effect |
| --- | --- | --- | --- |
| task | `v` | `set_description_mode` | open the pane and take its keys |
| description | `esc` | `set_task_mode` | back to task mode, pane stays open |
| description | `v` | `toggle_description` | close the pane and go back to task mode |
| description | `ctrl-d` | `description_scroll_down` | down half the pane's body |
| description | `ctrl-u` | `description_scroll_up` | up half the pane's body |

- `ctrl-d` and `ctrl-u` are `page_down` / `page_up` in `Mode::Any` and are
  shadowed here, so while the pane holds the keys the *table* cannot be paged.
  That is the trade this mode exists to make, and `esc` is one key away from
  undoing it. They are shadowed rather than given new keys because a reader who
  reaches for a half-page scroll reaches for `ctrl-d`.
- `j` and `k` are deliberately *not* shadowed. They move the task cursor through
  the `Any` fallback, the pane re-targets, and reading down a list costs no mode
  switches. Line-by-line scrolling of the text is not offered; the wrapped line
  count is in the title and half pages are what the milestone was asked for.
- `v` closes from inside the mode and opens from task mode, the way `g` does for
  the chart. `esc` leaves the pane open and hands the keys back, also like the
  chart, so a glance at a long description does not have to be dismissed to go
  on filtering.
- `o` (`open`, already bound in task mode) stays the escape hatch to the real
  thing: plain `notes` has no links or formatting, and the browser does.
- No action belongs in `is_task_view_action`. That list is for driving the task
  pane while the project list has focus; this mode has its own keys.

## 4. Where the text comes from

Asana sends `notes` only when asked, and it is not in `TASK_OPT_FIELDS`. It is
deliberately **not** added there:

- `TASK_OPT_FIELDS` is shared by the list, subtask, create, and update
  endpoints. Adding `notes` would put every description of every task in every
  selected project on the streaming load path — unbounded text, fetched for
  tasks nobody opened, paid for on every refresh
- the app already has the right-shaped request: `AsanaClient::get_task` fetches
  one task by gid

So a second, much smaller field list and a method of its own
(`src/asana/client.rs`, `src/asana/mod.rs`):

```rust
const DESCRIPTION_OPT_FIELDS: &str = "gid,notes";

/// One task's description, as plain text.
///
/// Its own method rather than a `notes` field on [`TaskDto`], and a `String`
/// rather than an `Option<String>`: the shared `TASK_OPT_FIELDS` does not ask
/// for notes, so a nullable field on the DTO would mean "not requested" at
/// every call site but one and "this task has no description" at that one —
/// and Asana answers an empty description as `""` anyway. Neither of these
/// can be read the wrong way.
fn get_task_description(&self, task_gid: &str) -> Result<String>;
```

- the request asks for notes and nothing else. The cache is keyed on the
  `modified_at` the **loaded record** already carries (§5), so the server's
  copy of it would be a second answer to a settled question — and, worse, one
  that can disagree with the first
- `FakeAsanaClient` gains `with_description(gid, text)` and a
  `description_calls()` accessor beside the existing `get_task_calls()`, which is
  what lets the tests in §8 assert *how many* fetches a burst of `j` cost

## 5. The state, and the fetch

`DescriptionState` in `src/app/description.rs` (new), held by `TaskState` and
reached as `app.tasks.description()`, exactly as `GanttViewState` is reached as
`app.tasks.gantt()` — it is a viewport over the loaded rows, not a property of
the data.

```rust
pub struct DescriptionState {
    visible: bool,
    /// The gid the pane is showing, and the scroll within it.
    target: Option<String>,
    scroll: usize,
    /// Fetched text, keyed by gid.
    cache: HashMap<String, CachedDescription>,
    /// The gid a fetch is out for, if any.
    pending: Option<String>,
    error: Option<String>,
}

struct CachedDescription {
    /// The record's `modified_at` when the fetch went out.
    modified_at: Option<String>,
    text: String,
}
```

- **The comparison is the invalidation.** A lookup asks the cache for the gid and
  checks the stored `modified_at` against the record's current one; a mismatch is
  a miss. Nothing has to remember to clear anything when an edit lands, which is
  the failure mode a separate invalidation hook would have.
- The timestamp is the **record's**, captured when the request goes out rather
  than read back with the reply. Two values that can disagree would give a cache
  that misses on every frame — a thread and a request per frame — and nothing
  later could settle it. Taking it from the record makes the hit reachable by
  construction, `None` included, which is its own test.
- `scroll` resets to `0` whenever `target` changes. Carrying a scroll offset from
  one task's description to another's would open the next one in the middle.
- `error` is held on the pane and drawn in the pane, not through
  `TaskState::edit_notice`. The notice box is for writes the user asked for and
  did not get; a read failing is the pane's own content, and it clears when the
  cursor moves to a row that loads.

The fetch follows `request_task_data` / `poll_task_data` in `src/app.rs`, down to
the generation counter:

- `App::description_receiver` and `App::description_generation`, beside the task
  data pair. A reply whose generation does not match is dropped, which is what
  stops a slow fetch from landing on a row the user has already left
- `App::request_description` starts it: no-op unless the pane is visible, the
  cursor names a task (`cursor_task_gid`, so the recently-edited pane works for
  free), and the cache misses. One `thread::spawn`, one `mpsc` reply, matching
  the existing shape
- `App::poll_description` is called from the same place `poll_task_data` is
- **it fires on a settled cursor.** `App::handle_key_event` already runs after
  every key, including the ones read outside the keymap, and already gates the
  config write-through on `!self.tasks.input_pending()` — the last key of a burst
  is the one with an empty queue behind it. The description request joins that
  gate, so holding `j` through thirty rows costs one fetch for the row you landed
  on, not thirty
- `refresh` (`r`) clears the cache along with the task cache, so a description
  edited in the browser can be re-read without restarting
- a failed fetch stores the message and clears `pending`; it is retried when the
  cursor returns to that row or on `refresh`, not on a timer

## 6. Geometry and rendering

`split_description` lives in `src/ui/description.rs` (new), beside the renderer
that uses it rather than in `src/ui/layout.rs` — the same call `split_sidebar`
makes in `src/ui/filter_sets.rs`, and for the same reason: this is a split of one
pane's region, not a region of the frame.

```rust
pub fn split_description(area: Rect, visible: bool, min_table_width: u16)
    -> (Rect, Option<Rect>);
```

- a share of the region, clamped: `DESCRIPTION_SHARE = 0.38`, bounded by
  `MIN_DESCRIPTION_WIDTH = 28` and `MAX_DESCRIPTION_WIDTH = 60`. A pane narrower
  than 28 wraps prose into a column of broken words; one wider than 60 is a wall
  of text and is taking the width from the table that names the rows
- if the table cannot keep `MIN_TABLE_WIDTH = 32` after the split, the pane is
  dropped for that frame and a `Chip::toned("description too narrow", Tone::Warn)`
  says so on the task pane — the chart's own degradation, reused
- `src/ui/runtime.rs` calls it on `regions.task_pane` **before**
  `render_task_table`, because the table has to be measured against the width it
  is actually getting. The chart sees a `TaskState` whose `gantt().visible()` is
  overridden to `false` while the pane is open (§7), so the two cannot both claim
  the space

`description_view(state, width) -> DescriptionView` resolves the state into the
drawable snapshot, and `render` draws it:

- the text is normalized once on arrival — CRLF to LF, tabs to spaces,
  trailing whitespace dropped. Blank lines are deliberately left alone there:
  how paragraphs and lists are spaced is a layout question, not a cleanup one
- `layout` turns the normalized text into lines. It reads each source line as
  prose or as a list item (`- `, `* `, `+ `, `• `, `1. `, `2) ` — the trailing
  space is what makes it a marker, so `-10 degrees` and a `---` rule stay
  prose), wraps each block through `text::wrap_to_width`, hangs a wrapped item
  under its own text, and puts one blank line between blocks — but never
  between two items of the same list
- the wrap is recomputed per frame against the current inner width, and `scroll`
  is clamped to `lines.len().saturating_sub(body_height)` afterwards. Narrowing
  the terminal makes the text longer, and a scroll offset past the end would show
  an empty pane
- `scroll_by(half_page)` is driven from the rendered body height, which only the
  renderer knows — the same division of labour `ensure_selected_visible` and
  `ensure_column_visible` already follow. The amount is
  `(body_height / 2).max(1)`, so a two-line pane still moves
- the four message states of §1 go through `chrome::render_pane_message`

## 7. Everything else that has to know

- `src/ui/task_table.rs`: `split_pane` returns `all` when the description pane
  is open, the one-line change that makes "the chart or the description, never
  both" true in the one place that decides the chart's width. Nothing else in the
  renderer changes — the chart is already `Option`, and `None` is the path that
  runs today
- `settings_chips` gains `description`, and only while the pane is open
- `src/ui/hints.rs`: `description_hints` — scroll, close, open in Asana, help —
  and a `Mode::Description` arm in the dispatch. The bar sheds from the right, so
  this is a short list on purpose
- `src/ui/help_overlay.rs`: `description_groups`, listing the mode's own keys and
  the globals that still work
- `src/config/mod.rs`: `[view].description`, a `bool` with `#[serde(default)]`
  beside `tasks`, `filters`, and `recent`. `[view]` is what is open, not where you
  were, so the flag persists and the scroll offset and the target gid do not. No
  header version bump: a version-3 file without the key is a valid version-3 file,
  and the default is the behaviour that file already had
- `App::apply_view_config` restores it and `App::stage_view_state` captures it —
  both, deliberately, since a field added to one and not the other is written and
  never read back
- at startup, a config with both `[gantt].visible` and `[view].description` true
  opens the description and leaves the chart's own flag alone, so closing the
  pane reveals the chart. The rule is the same at startup as it is at runtime

## 8. Tests

Unit, next to the code that changed:

- `src/app/description.rs`: the scroll clamps at both ends; `scroll` resets when
  `target` changes; a cache hit with a matching `modified_at` is a hit and the
  same entry with a changed one is a miss; a cleared cache is a miss
- `src/ui/description.rs`: `split_description` honours the share, both bounds,
  and the `min_table_width` floor; it returns `(area, None)` when invisible, and
  the two rects are adjacent and exactly fill the region
- `src/app/description.rs`: normalization — CRLF, tabs, trailing space, and a
  description that is entirely whitespace, which must read as empty
- `src/ui/description.rs`: `classify` on every marker shape and on the
  near-misses that are prose; paragraphs spaced the same from one newline and
  from two; a wrapped item hanging under its own text; a nested item keeping
  its indent on both lines; one list not spaced through; and the property that
  no laid-out line is ever wider than the pane
- `src/config/mod.rs`: `[view].description` round-trips, defaults to `false`, and
  is absent from a serialized default config
- `src/input/mod.rs`: `v` resolves to `set_description_mode` in task mode and
  `toggle_description` in description mode; `ctrl-d` resolves to
  `description_scroll_down` in description mode and `page_down` in task mode

Integration (`tests/description_keyboard_navigation.rs`, new, modelled on
`tests/gantt_keyboard_navigation.rs`):

- `v` from task mode opens the pane, enters the mode, and fetches once
- **a burst of `j` costs one fetch.** Queue thirty key events, assert
  `description_calls()` has length one and names the row the cursor landed on.
  This is the test the whole settled-burst design exists for
- revisiting a row fetches nothing; `r` clears the cache and the next visit
  fetches again
- `esc` leaves the pane open and returns the keys: `ctrl-d` pages the table again
- `v` from inside the mode closes the pane and returns to task mode
- a fetch that fails leaves the message in the pane and the session usable
- opening the pane while the chart is on hides the chart; closing it brings the

## 9. Comments

Added after delivery. The description and the comments are **one document**:
one scroll covers both, `line N/M` counts the lot, and there is no second pane
and no second key. A comment is an answer to what the description says, and a
reader moving between two panes to follow that is a reader doing the pane's
job.

### 9.1 Where they come from

`/tasks/{gid}/stories`, which is the task's whole activity feed — "changed the
due date", "added to a project", and every other thing that has ever happened
to it. `resource_subtype == "comment_added"` is the filter, and it is in
`STORY_OPT_FIELDS` for exactly that reason. A story with no text, or only
whitespace, is dropped too: it would cost a byline and a blank line to say
nothing.

- `AsanaClient::list_task_comments` is its own method rather than part of
  `get_task_description`. Different endpoint, it paginates, and most of what it
  answers with is thrown away.
- **Both reads go out on one worker thread**, in `App::request_description`,
  and come back as one `Result`. The pane has one state to be in: a
  half-loaded pane would have to say "here is the description, and the comments
  may or may not exist", which is not something a reader can act on. So either
  it has the task's text or it says why it does not — which is what
  `a_failed_comment_fetch_fails_the_pane_rather_than_half_filling_it` pins
  down.
- The comments ride in the same cache entry, under the same record timestamp,
  so the settled-cursor gate covers them unchanged: a burst of `j` is one
  description read and one comment read, for the row the cursor landed on.
- **A new comment does not invalidate the cache.** Asana bumps `modified_at`
  for field changes, and a story is not a field change, so a comment added
  while the session is open is not noticed until `r`. Living with it: the
  alternative is re-reading the stories of the row under the cursor on a timer,
  which is a request per few seconds to catch something the reader can ask for.

### 9.2 How they read

```
Previous run's notes are in the 4411 folder.

────────────── 3 comments ───────────────
Morgan Ellis · Jul 28
Protocol draft is in the shared folder.
Two things still open:

- the assay range on page 4
- whether we need a second reviewer

Alex Chen · Aug 2
Second reviewer confirmed.
```

- the heading is a rule with the count in words, centred, and it degrades to
  the bare label in a pane too narrow for a rule
- a byline is the author in `subtitle` and the date in `muted`, separated by
  the same `·` the chips use. **The date is absolute**, not relative: a comment
  is always in the past, so it has no urgency to report, and `3 days ago` is
  worse than a date when the comment above it is from last year. The year
  appears only when it is not this one — `date::short_date_from`, moved out of
  `task_table` into `ui/date.rs` so the chart's window and a byline agree
- a comment with no author reads `(unknown)` rather than blank. An integration
  posting through the API is the usual cause, and a byline missing its left
  half looks like a bug
- an unparseable timestamp drops the date rather than printing the raw value: a
  byline is two facts, and one of them being unreadable is better said by its
  absence
- **comments are laid out by §6's `layout`, same as the description** — people
  write lists in comments too, and a comment's wrapped bullet has the same
  problem a description's does
- one blank line between comments, none after the last. `BodyLine` is the
  semantic line type this needs: prose, heading, and byline are styled
  differently, so the layout says *what* each line is and `render` says how it
  looks. That keeps every wrapping test free of a theme

### 9.3 Empty means nothing to read

`DescriptionContent::Empty` now means **no description and no comments**. A
task with three comments and no description has plenty to say, and reporting it
as empty would hide all of it — so the empty message is
`(no description or comments)` and `Body { notes, comments }` carries the case
where either half is empty but not both.

## 10. Acceptance criteria

- `v` in task mode opens a description pane to the right of the table and takes
  its keys; `r` still refreshes from task mode
- the pane shows the description of the row under the cursor, and follows the
  cursor as `j` and `k` move it
- `ctrl-d` and `ctrl-u` scroll the text by half the pane's body, clamped at both
  ends, and the title reports the position
- a description is fetched at most once per task per session, on a settled
  cursor, and the task-list request is unchanged
- `esc` hands the keys back with the pane still open; `v` closes it
- the pane says something useful when the text is loading, empty, absent, or
  failed to load
- the task's comments are shown under its description, each with who wrote it
  and when, and a task with comments and no description is not reported empty
- paragraphs are separated by a blank line however the description was typed,
  a wrapped list item hangs under its own text, and no line is ever wider than
  the pane
- the chart and the description never share the pane, and closing the description
  restores the chart unchanged
- the pane's open/closed state persists across runs; the scroll and the target do
  not
- with the pane closed, every rendered frame is byte-identical to the frames
  before this milestone, and every existing snapshot passes unchanged
