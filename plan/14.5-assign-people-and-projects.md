# Milestone 14.5: Assign people and projects ✓

[← all milestones](../plan.md)

Delivered. Seven deliberate deviations from the plan below.

1. **`resolve_assignee` survives as the fallback for text the candidate list
   cannot place.** §2.1 says nothing is entered that is not a candidate, and
   for names that is what happens. An email address is not a name: it is a
   handle Asana accepts and no directory lists, and Milestone 14 shipped it.
   So the assignee commit resolves against the candidates first and through
   `resolve_assignee` second, which is also where the refusal message for a
   name nobody has comes from.
2. **The workspace directory is fetched synchronously, the first time an
   editor needs it.** §2.2 says "cached for the session" without saying when
   it is filled. Lazily, and on the UI thread: most sessions never reassign
   anything, so a request at startup is a request nobody needed — and an
   editor that opened before its candidates arrived would refuse every name
   typed into it. A failure is cached as an empty directory, so a workspace
   that will not answer is asked exactly once and the picker falls back to
   the people the loaded tasks name.
3. **The candidates arrive through `EditContext`.** §4 says they are supplied
   when the editor opens, which they are, but the plan leaves the route open.
   `EditContext` already exists to carry what resolving an edit needs and the
   task pane does not own, so the project list and the directory travel
   beside `today` and the current user rather than through a second channel.
4. **A project the session never loaded is kept and never removed.** A record
   can hold a project gid whose name nothing on screen can resolve. It shows
   as the gid, is not a candidate, and — this is the part that matters — the
   removals a commit produces are restricted to projects the editor could
   have *offered*. Without that, applying one cursor row's project list to a
   selection would quietly take other tasks out of projects nobody could see.
5. **`commit_cell_edit` answers with two lists.** §2.3 says project membership
   is not a `TaskFieldEdit`; it follows that a commit cannot be a
   `Vec<TaskEdit>` either. `CommittedEdits` holds both halves, and `App`
   dispatches each to its own endpoint. They rejoin at the reply:
   `PendingEdit` is what keeps one burst counter, one border chip, and one
   rollback path across both kinds of write.
6. **The pane draws the newest four and counts the rest.** §3 caps the list at
   twenty and sizes the pane "to its contents up to a few rows", which
   together would leave sixteen rows remembered and undrawable. The list is
   still twenty, the pane draws four, and the border says how many are
   hidden. `layout::regions` therefore takes the row count rather than
   deciding the cap: how many rows are worth showing is the pane's own
   judgement, and only the geometry — that the height comes out of the task
   pane, and that the table keeps a minimum — belongs in `layout`.
7. **The pane holds what the *view* stopped showing, not only what the filter
   excludes.** §3 says filter. But moving a task out of the project you are
   looking at drops it from the loaded target set rather than from the filter
   panel, and that is one of the two edits §1 names as the reason the pane
   exists. So membership is "in the recently-edited list and not a row in the
   table", whatever removed it — and the records come from the cache rather
   than the visible dataset, because a task that left the target set is no
   longer in the dataset at all.

## The plan as written

Goal:

- make `Assignee` and `Projects` editable, with completion over the names that
  actually exist
- offer the same completion in the filter panel, as a new `list` match mode
- keep a task you just edited reachable after your own filter hides it

## 1. Why these together

[Milestone 14](14-edit-tasks.md) made the table writable and stopped at the two
fields that are not free text. `Assignee` is typed today and resolved at commit
against the names that happen to be loaded; `Projects` refuses outright —
`project membership is not editable yet`. Both are references to something with
a name and a gid, and both want the same editor.

They are also the two edits most likely to make a task vanish. Reassign a task
while filtering on `assignee:me`, or move it out of the project you are looking
at, and the row leaves the table under the cursor — which is the one moment the
edit is least finished. The completion editor and the recently-edited pane are
one milestone because the second is the price of the first.

Once the editor exists, the filter panel wants it too: `Assignee` is the one
filter row whose values are real names out of a directory, and typing a fuzzy
pattern at a list of people you could have picked from is the same small
indignity in the other pane.

## 2. Completion editor

A fourth editor kind beside `Text`, `Options`, and `Date`: a field whose value is
a list of **items**, each of which is a name the backend knows, typed with
completion. It has two homes — the table's cell editor (§2.1–2.3) and the filter
panel (§2.4) — which is the same arrangement the text buffer and the date picker
already have.

- **Assignee** is a list capped at one. Committing an empty list unassigns.
- **Projects** is a list of any length. A task with no project is not a thing
  Asana will store, so committing an empty list is refused with a message rather
  than sending a removal that would fail.

### 2.1 The keys

| key | what it does |
| --- | --- |
| type | filters the candidates, in place |
| `tab` | complete the typed prefix to the next candidate |
| `shift-tab` | complete to the previous candidate |
| `enter` | commit the whole list |
| `esc` | throw it away |
| `backspace` | delete a character, or the item before the caret when there is none |
| `left` / `right` | move the caret between items |
| `ctrl-l` | clear every item |

`tab` cycles rather than picking: pressing it repeatedly walks the candidate
list with the prefix intact, so a wrong first match costs one more keystroke
instead of an undo. Nothing is entered that is not a candidate — a typed prefix
with no match commits nothing and says so. All of it is configurable, like every
other binding.

### 2.2 The candidates

- **Projects** come from the project list, which is already loaded and already
  on screen in the other pane. No new fetch.
- **Assignees** come from the workspace, which is a fetch we do not make yet:
  one `list_users` on the client trait, cached for the session, falling back to
  the names carried by loaded tasks when it fails. The directory built from
  loaded tasks today can only offer people who already have a task in view,
  which excludes the most common reason to reassign one.
- `me` stays a candidate for `Assignee`, resolved through `EditContext` the way
  the commit path already resolves it.

The candidate list is shown as an overlay window, positioned and styled like the
date picker: the cell is too narrow to list names in, and the picker already
taught where to look for the options a field offers.

### 2.3 The write

Project membership is not a field on the task, so it is not a `TaskFieldEdit`
the way the others are. A commit resolves to a set of adds and a set of removes,
each of which is one request. That needs `post_json` on `Transport` and the
`addProject` / `removeProject` endpoints; the optimistic update writes
`project_gids` and `projects` on the record and the rollback puts both back.

One consequence worth stating: the cache is keyed by the target that loaded a
task, so a task removed from the project in view is still in that project's
cached page. The table has to drop it from the rebuild without waiting for a
refresh, which is the same mechanism §3 needs anyway.

### 2.4 In the filter panel: the `list` match mode

`Assignee` is the one filter row whose values are a closed set of real names
that nobody wants to spell. It gains a fourth match mode beside `fuzzy`,
`contains`, and `regex`:

| mode | what `alex` means |
| --- | --- |
| `fuzzy` | the assignee name fuzzy-matches `alex` |
| `contains` | the assignee name contains `alex` |
| `regex` | the assignee name matches the pattern |
| `list` | the assignee is Alex Chen — or any of the other people picked |

Only `Assignee`. `Projects` keeps the three string modes it has: which projects
are in view is what the project pane is for, and a second place to answer it
would be two controls fighting over one question. The other string rows are free
text with no directory behind them, so there is nothing to complete against.

Several picked people are ORed, the way a `Labels` row already ORs its values.
The row's negation still means what it says — a negated `list` is "none of
these" — and require-empty is still "unassigned", unchanged.

Three things fall out of the panel's existing design rather than needing new
machinery:

- **The value is still the text.** A `Labels` row mirrors its values into the
  buffer joined with `" | "`, and the date picker writes into the buffer too;
  `list` does the same. The saved-set schema does not change — the picked names
  are the `query` string, with `match = "list"` beside them.
- **Matching is by name, exactly.** Not a pattern: that is the entire point of
  having picked from a list. `me` resolves to the logged-in user at match time,
  not when it is picked, so a saved set stays personal to whoever loads it.
- **`list` joins the mode ring.** `cycle_filter_string_mode` offers it on
  `Assignee` and skips it everywhere else, and it gets a `search_list` action
  beside `search_fuzzy` / `search_substring` / `search_regex`. Add `"list"` to
  `SAVED_MATCH_MODES`; a saved `match = "list"` on a row that cannot offer it
  parks the same way an unknown field key already does.

## 3. Recently edited

A pane between the top pane and the task table, holding tasks edited this
session that the current filter no longer shows.

```
┌ Projects ──────────────────────────────────────────────────┐
│  ● ★ Northwind BTX 4412                                    │
└────────────────────────────────────────────────────────────┘
┌ Recently edited ─────────────────────── 2 hidden by filter ┐
│▍  Ship release candidate  │ Alex Chen │ Today │ ○ │ Nor…   │
│   Label the retention sa… │ Jo Park   │ Oct 9 │ ○ │ Bac…   │
└────────────────────────────────────────────────────────────┘
┏ Tasks ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 9 tasks · row 1 ┓
┃   Draft the assay validation protocol  │ Priya Raman │ …   ┃
```

- It lists the same columns as the table, in the same widths, so the two read as
  one surface. No grouping, no headers of its own: newest edit first.
- A task is in it when it was edited this session **and** the current filter
  excludes it. Edit it back into the filter — or change the filter — and it
  leaves on the next rebuild.
- The list is capped (twenty is plenty) and dies with the session. It is not
  persisted: "what I was just doing" is not a thing to restore three days later.
- The pane sizes to its contents up to a few rows, and takes that height from
  the task pane, not from the top pane. `layout::regions` is where this happens;
  nothing else should be computing pane geometry.

### 3.1 The sticky cursor

The cursor is currently a row index into one table, restored after a rebuild by
looking its gid back up. It becomes a cursor into one of *two* lists, still
restored by gid.

When a rebuild would lose the cursor's task from the table, and that task is in
the recently-edited list, the cursor moves into the pane and lands on that task
— the same task, in the same place on screen, still under the same keys. It does
not fall to a neighbouring row and leave the edit behind. Every other fallback
in `refresh_table` stays as it is.

`e`, `d`, and `space` work in the pane exactly as they do in the table: finishing
an edit is the whole reason the row is still on screen. `j` and `k` walk out of
the pane and into the table, because the two lists are vertically adjacent and
continuous motion is what that promises.

### 3.2 Visibility

- A binding toggles the pane. Hiding it while the cursor is inside returns the
  cursor to the table, at the row the task would have sorted near.
- An edit that hides the cursor's task **shows the pane regardless** of the
  toggle, because the alternative is a cursor the user cannot see.
- With nothing in the list the pane is not drawn, toggle or no toggle.

## 4. Implementation notes

- The completion editor is a state machine beside `text_edit.rs` and
  `calendar.rs`: one buffer, a list of items, a candidate source, no UI.
  `src/app/autocomplete.rs`, owned by `CellEditor` and by the filter row alike —
  one implementation with two callers, which is the whole reason the filter
  panel gets this for nearly free.
- Candidates are a `Vec<(handle, display)>` supplied when the editor opens, not
  a client call from inside it. The editor stays testable without a backend.
- `Projects` needs its own edit type rather than being forced into
  `TaskFieldEdit`; keep the add/remove pair in `domain/task_edit.rs` so the
  rollback is still the same code path as the apply.
- The recently-edited list belongs in `TaskViewState` beside the selection, and
  the pane renders through `task_table`'s existing row rendering rather than a
  second implementation of it.
- Reuse `Mode::TaskEdit`. A fourth mode for a fourth editor would double the
  keymap for no new vocabulary.

## 5. Acceptance criteria

- `Assignee` and `Projects` both open a completion editor, and both commit
- `tab` completes a typed prefix; repeated `tab` cycles the candidates
- the `Assignee` filter row offers a `list` mode, and only that row does
- a `list` row matches the picked people exactly, ORs several of them, and
  negates to "none of these"
- a `list` row saves, reloads, and round-trips through a named filter set
- items can be deleted with `backspace` and walked with the caret keys
- a project can be added to and removed from a task, and a failure rolls back
- unassigning works; emptying `Projects` is refused with a message
- a task edited out of the current filter appears in the recently-edited pane
- the cursor follows it there, and the pane shows itself when the cursor lands
  in it
- the pane can be toggled, and its binding is configurable
- a task that matches the filter again leaves the pane
- tests cover the completion state machine, project add/remove including
  rollback, `list`-mode matching and its saved round-trip, the recently-edited
  list's membership rules, and the cursor handoff between the two lists
