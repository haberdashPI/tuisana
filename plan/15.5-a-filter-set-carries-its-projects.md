# Milestone 15.5: A filter set carries its projects ✓

[← all milestones](../plan.md)

Delivered, then revised on review. The plan below is the plan as written; the
two sections under it are what was actually built.

## Revised on review: the selection has one home

The first pass kept `[view].projects` and let a named set *also* carry a
project list, with "absent" meaning "no opinion". That left two places a
selection could live and a set that could decline to have one — vestigial
behaviour that only makes sense to someone who used the older TUI. So:

1. **`[view].projects` is gone, and the config header goes to version 3.**
   §2.1 argued the header should *not* move, on the grounds that a v2 file
   without the key is still a valid v2 file. That holds only while the global
   list survives to be the fallback. Removing it changes what an existing file
   means, which is exactly what a version is for. `Header::CURRENT_VERSION` is
   `3.0`, `OLDEST_VERSION` stays `1.0`, and `migrate` runs the version-1 steps
   and the version-2 step independently, so a v1 file gets both and a v2 file
   gets the second. The prompt describes only the changes the file in front of
   it is behind on.
2. **A version-1 or -2 selection is moved, not dropped.** It goes onto the
   entry `[view].filter_set` named — that entry *was* the panel on screen, so
   the selection beside it was its selection — unless that entry already
   states one, in which case the file is right already. With nothing bound it
   goes to the scratch entry (3). `ViewConfig::legacy_projects` is read and
   never written, and exists only to make that move possible: ignoring the key
   instead would have thrown away the selection someone uses every day.
3. **An unnamed panel's selection lives in a reserved `[[filter_set]]`**,
   marked `scratch = true`. One place a selection can ever be, rather than a
   second home in `[view]`. It is hidden from the sidebar, never addressed by
   a digit, and never found by name — the flag is its identity, so its name
   cannot collide with a real one. It holds a selection and **nothing else**:
   its `sets` stay empty, the panel is still genuinely unnamed, and the
   discard confirmation still means what it says.
4. **`projects` absent now means "none", not "no opinion".** With no global
   list there is nothing to inherit, so loading any entry replaces the
   selection — and an entry migrated from an older file loads to nothing
   selected. The `Option` survives in the schema for one reason only: so
   *migration* can tell an entry that never had the key from one saved
   selecting nothing. Runtime reads it through `NamedFilterSet::projects`,
   which reads a missing key as empty. §2.1's absent/empty distinction and
   §6's conditional confirmation lines both go with it — the window now always
   names what the entry will select.
5. **Nothing is in play until it is selected, and the filter view is gated on
   it.** `task_target_projects` used to fall back to the row under the cursor
   when the selection was empty. That was the last implicit project list in
   the app, and it had to go with the global one: while it existed the user
   was never actually required to select anything, so "the empty project
   state" was not a state. With it gone, `App::project_gate_closed` is real,
   `set_filter_mode` refuses in it with a notice, and `enforce_project_gate`
   closes a filter view that `n` or a project-less load has pulled the ground
   out from under. The task view is deliberately **not** gated: its empty
   table already reads `select projects, then press t`.

Two consequences worth stating, because they are costs and not wins:

- `n` now ejects you to the project view, since it clears the selection. The
  flow for a second set is `n`, pick projects, `f` — which is the forcing the
  gate exists for, but it is one more step than before.
- A session that never names a set still writes a `[[filter_set]]`, because
  that is where its selection goes. The file grows an entry the user did not
  type a name for; `scratch = true` is what labels it as the app's.

## What was decided differently while building the first pass

1. **The projects half compares against a baseline, not against the entry on
   disk.** §7 says it "compares the live selection against the entry's list
   independently of the flag". That cannot hold together with §2.2:
   `stage_named_filter_set` runs after *every* settled burst, so comparing
   against the entry would drop a gid the workspace no longer returns on the
   very keypress that loaded the entry — which is exactly what §2.2 forbids.
   `App::bound_projects` holds `(entry name, selection as the binding last
   agreed it)` instead, and a *change* from that baseline is what writes. The
   name in the pair is what makes a load, a save under a new name, and the
   startup restore re-baseline without each site having to remember to, and
   the projects half still has no dirty flag.
2. **`restore_selection` resolves `me` as well.** §12 puts the token's
   resolution in `apply_filter_set_selection`; the shared private helper the
   plan asks for is where it actually sits, so `[view].projects` goes through
   it too. An Asana gid is numeric, so that list can never hold `me` by
   accident, and the alternative was two spellings of one translation.
3. **The prompt's return mode lives on `App`, not on the prompt.** §12 says
   "the sidebar prompt carries the mode it interrupted". `SidebarPrompt` is
   `TaskState`'s and knows nothing about `Mode`, while all three prompts are
   opened and answered in `App` — so `App::prompt_return_mode` carries it,
   written by `enter_sidebar_prompt` and read by `leave_sidebar_prompt`.
4. **The project pane's chip is drawn whatever the list is doing.** §12 puts
   it in `counts`, which returned nothing at all for a loading, empty, or
   errored list. The whole point of the chip is that it cannot be turned off,
   so `counts` now builds its chips up and appends the name outside that
   guard.
5. **The sidebar's project count and the confirmation's entry come in as
   arguments.** `render_filter_sets` reads `TaskState`, which does not know
   the project selection, so the count is passed from the renderer — the same
   way `confirm_view` now takes the saved entries, since it has to find the
   loaded one's `projects` to decide whether to say anything about them.
6. **Collapsing duplicates happens at parse, not in `validate`.** §2.1 calls
   it validation, but `Config::validate` takes `&self`. `NamedFilterSet::
   normalize` runs in `from_toml_str` between `migrate_v1` and `validate`:
   collapsing a duplicate is the parse deciding what the file meant, where
   refusing a blank entry is a rule it has to pass, and that stays in
   `validate`.
7. **An entry that selects nothing says so in words.** §6's mockup reads
   "`Blocked` selects its own 2 projects", which for `projects = []` would
   read "its own 0 projects". It reads "`Blocked` selects no projects at all",
   the same instinct as §3.3's `no projects`.
8. **Sixteen bindings, not seven.** §4 counts `1`-`9` as one key. Each digit
   is its own command, as it already is in filter mode, so the project arm of
   the defaults and of `tuisana.toml.example` gains sixteen entries.
9. **`run_session` grew a required `HostEffects` argument.** Not part of this
   milestone's scope, but found by it: the session loop shelled out to `open`
   and wrote the real clipboard, so a test that reached `Action::Open` opened
   a browser window on the machine running `cargo test`. The gate in (5)
   made one such test take a different branch and it surfaced immediately.
   `SystemHost` is the real one and `run_app` is the only thing that builds
   it; `RecordingHost` writes both down and does nothing. Required rather
   than defaulted, because the hazard was precisely an implicit default.

Two things found along the way:

- **Test config files collided.** `config_on_disk_with` named its temp file
  from `SystemTime::now()` alone; two tests running in the same tick shared a
  file and failed each other intermittently. The name now carries a
  process-wide counter as well.

- **The sidebar reads `0 sets · 0 active` in a session that has never opened
  the filter panel.** `TaskFilterEditor::sets` is empty until the panel is
  built from the loaded dataset, which no longer happens off screen now that
  the sidebar is visible in the project view from the first frame. Left as it
  is: it is honest about a panel that does not exist yet, and giving the
  editor a set before the data arrives would mean deciding what rows it has
  before the custom fields are known.

## The plan as written

Sections 2.1, 6, 9, and 12 are superseded by the revision above: the header
*does* move, `[view].projects` is gone, "absent" no longer means "no opinion",
and the confirmation's project lines are unconditional. The rest stands.

Goal:

- make the project selection part of a named filter set, so one digit moves
  both halves of the question
- show the `Sets` sidebar in the project view as well as the filter view, from
  the one toggle that already opens it
- keep the selection writing through to the bound entry, exactly the way a
  filter field already does

## 1. What this reverses, and why

[Milestone 13.5](13.5-named-filter-sets.md) drew the line deliberately, and the
README still says so:

> It is deliberately *not* the sort, the grouping, the completed filter,
> subtask visibility, or the project selection. Those are the other half of the
> screen: a saved filter is a question about tasks, not about which projects it
> is asked of.

The sort and the grouping belong on that list. The project selection does not.
A sort is how you are reading the answer; the selected projects are the first
clause of the question — `Assignee: alex` means nothing until something says
*where*. Saving the second clause and not the first produces a set that is only
half a set: load `Sprint triage` with yesterday's projects still selected and
you get a confident, precisely filtered, wrong table. And it is the clause that
costs a network fetch, so it is the expensive half to get wrong.

So a named filter set grows a project list, and the window that shows the sets
gains the right to be on screen in the project view, where that list is edited.
Three things follow, and they are the whole milestone:

1. the entry on disk carries projects (§2)
2. the sidebar appears in both views, from one toggle (§3–§4)
3. loading a set moves the selection, and moving the selection writes back
   (§5–§8)

The code comment this contradicts is in `src/app/task.rs`, on the filter
panel's `Projects` row: it stays free text because "which projects are in view
is what the project pane is for, and a second control answering the same
question would be two controls fighting over it". The two controls are real and
the row keeps its job — but after this milestone they are not fighting, they
are layered, and §10 is where that is written down.

## 2. What a named set holds now

### 2.1 The schema

One optional list on the entry, above the tabs, because the selection is one
list per *panel* and not one per tab. Tabs OR, and a fetch scope cannot: there
is one set of projects being read, whatever the tabs then ask of it.

```toml
[[filter_set]]
name = "Sprint triage"
projects = ["me", "1201", "1202"]

  [[filter_set.set]]

    [[filter_set.set.field]]
    key = "assignee"
    query = "alex"

  [[filter_set.set]]

    [[filter_set.set.field]]
    key = "due"
    query = "..today"
```

- **Absent and empty mean different things.** `projects` missing is "this entry
  has no opinion": loading it leaves the selection exactly as it was. `projects
  = []` is "select nothing", which loads to an empty table. The distinction is
  what lets every `[[filter_set]]` already on disk keep working unchanged —
  they all pre-date this milestone, and every one of them means "no opinion".
  It is also why the config header does *not* go to version 3: a v2 file
  without the key is still a valid v2 file, so there is nothing to migrate.
- **`w` always writes the key**, even as `[]`. An entry saved from now on is
  unambiguous; only a hand-written or pre-existing one is silent.
- **Gids, not names**, matching `[[project]]` and `[view].projects`. A project
  is renamed far more often than it is recreated, and the two other places the
  file names a project already name it by gid.
- **`me` is the assigned-to-me row.** Its `Project.id` is the *logged-in user's*
  gid, so writing it raw would bake one person into a shared file and a set
  loaded by anyone else would quietly select a project that does not exist. The
  `Assignee` row already resolves `me` at match time for this reason, and this
  is the same token doing the same job. Asana gids are numeric, so `me` cannot
  be mistaken for one.
- **Written in a stable order:** `me` first, because the row is pinned first in
  the list, then the gids sorted. `current_view_config` already sorts for this
  reason — a `HashSet` has no order, and without it the same selection rewrites
  the file differently run to run.
- **Validation** rejects an entry that is blank after trimming, and collapses
  duplicates rather than refusing them: a hand-edited file that names a project
  twice meant it once. Nothing checks that a gid exists, because at parse time
  the workspace has not been asked yet.

### 2.2 A gid the workspace no longer returns

Dropped when the set is applied, kept on disk. The project list holds the whole
workspace, so an unrecognised gid is genuinely gone rather than merely not
loaded yet — but *applying* a set is not consent to rewrite it, and a project
you lost access to for a week should not cost you the entry. It goes only when
you next change the selection while the entry is bound, which is a deliberate
edit of that entry.

This is the same instinct as 13.5's rule for custom fields — "a filter naming a
custom field from a project you have not loaded is *kept*, not dropped" — with
one difference worth saying out loud: a custom field is re-resolved every time a
project's fields arrive, and a project gid is resolved once, because there is
one project list and it arrives once.

## 3. The sidebar in both views

### 3.1 It is the top pane's sidebar now, not the filter panel's

Today the split lives inside `render_filter_pane`, with the comment "the
sidebar belongs to the panel, not to the frame". Half of that stays true — it
is still not a frame region, and `layout::regions` does not learn about it —
but it now belongs to whichever pane the top window is holding.

```
┌ Sets ──────────┐┏ Projects ━━━━━━━ 12 shown ━ 4 selected ━ Sprint triage ┓
│ ▸ Sprint triage││  ◆ ☆ No Project (Assigned to Me)                       ┃
│   2 sets · 3   ││  ◆ ★ Platform                                          ┃
│   4 projects   ││    ★ Growth                                            ┃
│ ───────────────││▍ ◆ ☆ Infra                                      hidden ┃
│ 1 Blocked      ││  ◆ ☆ Docs                                             ┃
│ 2 Overdue mine ││    ☆ Archive                                          ┃
│ 3 ▸Sprint triage   ☆ Platform (old)                                     ┃
└──────── 1-4 of 4┛━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┛
```

One flag, one key: `b` toggles the sidebar and `[view].filter_sidebar` records
it, as now. Switching between `p` and `f` does not open or close it — "once
toggled to show up" means it stays up across the mode switch, which is the
whole point of tying the two views to one window.

It is still **never focused** in either view. `j` and `k` walk the project rows
in project mode exactly as they walk the filter rows in filter mode, and the
thin border is what says so.

### 3.2 It gives way at a different width in each view

`MIN_FILTER_WIDTH` is 64: the filter panel's three columns of label, match
mode, and value are what it is *for*, and below that the sidebar is dropped
rather than squeezing them. A project list is one column of names, so it gets
its own floor — `MIN_PROJECT_WIDTH`, 32, enough for the marker gutter, a
readable name, and the `hidden` chip. At eighty columns the sidebar therefore
stays up in the project view and gives way in the filter view, which is correct
rather than inconsistent: the two panes need different amounts of room to mean
anything.

### 3.3 A fourth header line

The pinned header gains the count that is now part of the panel:

```
│ ▸ Sprint triage│
│   2 sets · 3   │
│   4 projects   │
│ ───────────────│
```

A fourth line rather than a longer third one: the sidebar is 24 columns, `2
sets · 3 active` already fills most of it, and the abbreviations that would fit
all three counts on one line stop being words. It costs one numbered row on a
short terminal, which is the price. It reads `no projects` at zero rather than
`0 projects`, because that line is then the explanation for an empty table and
is worth a sentence rather than a number.

### 3.4 The project pane says which set the selection belongs to

A chip on the project pane's top border, carrying the loaded entry's name and
nothing when the panel is unnamed — `12 shown ━ 4 selected ━ Sprint triage`.
Without it, `space` in the project view silently edits a file whenever the
sidebar happens to be closed. The sidebar's pinned header says the same thing,
but the sidebar is the thing that can be turned off, and this cannot.

The `w` and `d` prompts keep riding the sidebar's bottom border. When the
sidebar has given way for width they borrow the project pane's bottom border,
the way they already borrow the filter rows' — and there they displace the
project search footer for as long as the prompt is open. A prompt is being
answered; a search string is being remembered.

## 4. The keys in the project view

Seven keys, all of them the sets keys they already are in filter mode:

| key | what it does |
| --- | --- |
| `b` | toggle the sidebar |
| `1`–`9` | load the entry at that position in the visible window |
| `<` `>` | page the window |
| `w` | save the panel under a name |
| `y` | copy to new |
| `n` | start a completely fresh panel |
| `d` | delete the loaded entry |

All seven are unbound in project mode today, so nothing is displaced and
nothing has to be relearned: the same key does the same thing in both views.
Each is a second `Bind::with_mode(..., Mode::Project, ...)` beside the existing
`Mode::Filter` one, and stays configurable like everything else.

What deliberately does **not** come across is the per-tab half of the panel:
`a` and `x` add and remove a tab, `h` and `l` move between them, `~` negates
one, and `e`, `s`, and `!` act on a filter row. Those are about fields, there
are no fields and no tab strip in the project view, and four of those letters
already mean something in project mode — `a` selects every visible project and
`h` hides the selection. The project list's own keys keep every letter they
have.

The hint bar follows the filter view's pattern: `sets` is always offered, so
the feature is discoverable, and `1-9 load`, `save`, `new`, and — once
something is bound — `copy to new` and `delete` appear only when the sidebar is
open and they have somewhere to act. The help overlay's project-mode arm gains
the same seven.

## 5. Loading a set moves the selection

A digit now does three things: it replaces the panel, it replaces the
selection, and it starts the fetch the new selection implies.

- The fetch needs no new machinery. Every action already runs between
  `task_targets_before` and `update_task_data_after_action`, which compares the
  target projects before and after and starts a fetch, or marks the table out
  of date when the task pane is closed. A load that changes the selection is
  exactly the case that pair was written for.
- **The load pushes the selection history.** `u` undoes it and `ctrl-y`
  redoes it, like every other selection change you made this session. The
  startup restore deliberately pushes nothing — "`u` undoes what *you* did this
  session, and restoring the view is not that" — but a digit is a keypress in
  the session, so it does. This is load-bearing for §6: it is what makes the
  selection half of a load recoverable when the filter half is not.
- `u` undoes the selection alone. It does not unload the set, and the entry
  then has the undone selection written back to it, because a bound entry is a
  file you have open and `u` is an edit like any other. The asymmetry is worth
  stating in the README rather than designing away: the two halves have
  different undo stories because only one of them ever had an undo.
- The cursor stays on the project it was on, through the same
  `rebuild_visible_projects` path `restore_selection` uses.
- A set whose `projects` key is absent leaves the selection, the history, and
  the fetch untouched (§2.1).

Loading from the project view stays in the project view. Today's
`commit_filter_set_load` calls `set_filter_mode` on its way out, which would
swap the project list away under the key that was pressed in it — so the
prompt remembers the mode it interrupted and goes back to that one.

## 6. The confirmation gains two lines, not a new trigger

The condition for asking stays what it is: an **unnamed panel that is
filtering**. A bound panel is already on disk and an empty one has nothing to
lose, as before — and a selection is not added to the test, because a selection
is nearly always there. Making the common opening move (`p`, `b`, `1`) ask a
question every time would spend the prompt's credibility on the case that is
never a mistake. The filters are the half with no undo; that is what the window
is for.

What changes is that the window now says what else is about to happen, when the
entry it names carries projects:

```
┌ Discard filters? ───────────────────────────────┐
│                                                 │
│ This filter panel has no name, so the           │
│ 3 filters it is holding exist nowhere else.     │
│                                                 │
│ Blocked selects its own 2 projects.             │
│ u in the project view puts yours back.          │
│                                                 │
│   y         discard them and load Blocked       │
│   n / esc   keep what is on screen              │
│                                                 │
└─────────────────────────────────────────────────┘
```

Both extra lines are omitted for an entry with no `projects` key, which is
every entry written before this milestone.

## 7. Writing through from the project view

`space` on a project while `Sprint triage` is loaded edits `Sprint triage`, on
disk, the same way typing into a filter field does. Everything that moves the
selection writes through: `space`, `a`, `!`, `@`, `i`, `c`, `u`, `ctrl-y`.

Two details make this nearly free:

- **The comparison is the whole test, so the selection half needs no dirty
  flag.** `stage_named_filter_set` bails early on `filter_set_dirty`, which the
  filter editor sets; the project list has no such flag and should not grow
  one. Instead the projects half compares the live selection against the
  entry's list independently of the flag, which is cheap — two short sorted
  `Vec<String>`s — and is already the safety net that makes the over-eager
  dirty flag safe on the fields half.
- **It is still one write per settled burst.** `stage_named_filter_set` and
  `stage_view_state` both run once when the key queue empties, and both are
  staged before either is written. Holding `a` then `i` then `c` costs one
  file write that moves both `[[filter_set]]` and `[view]`.

An entry with no `projects` key gains one the first time the selection moves
while it is loaded. That is the intended upgrade path: the key appears when you
first express an opinion through it.

## 8. `n`, `y`, `w`, and `d` under the new definition

- **`n` clears the selection too.** It means "start from nothing", and after
  this milestone the projects are part of what there is. Leaving them behind
  would make `n` a half-measure of exactly the kind §1 is about. The cost is
  real — an empty table, and a reselection before anything loads — and the
  answer is that `u` puts the selection straight back, because `n` pushes the
  history for the same reason a load does.
- **`y` (copy to new)** keeps what is on screen, which now includes the
  selection, and unbinds. Nothing to decide.
- **`w`** writes the live selection into the entry it saves or overwrites,
  always including the key (§2.1).
- **`d`** deletes the entry and unbinds. "The panel keeps what it is showing"
  already covers the selection: it stays selected, it is simply no longer
  written anywhere.

## 9. Startup

`[view]` already restores the panes and binds the panel before Asana has been
spoken to, and the selection lands later, in `load_projects`, because it needs
a project list to be filtered against. One rule decides what it restores:

- if `[view].filter_set` names an entry and that entry **has** a `projects`
  key, the entry's list is what is applied
- otherwise `[view].projects` is, exactly as today

The entry wins because the filter *fields* already come back from the entry and
not from `[view]`, and a hand-edited `projects` list should take effect for the
same reason a hand-edited field does. Write-through keeps the two in step
anyway, so they can only disagree in a file someone edited — which is the case
the rule is for.

`[view].projects` stays, unchanged in meaning: it is the selection of an
unnamed panel, which has nowhere else to be recorded.

## 10. The `Projects` filter row stays, as a narrowing

The row is not the selection and does not become it. They answer different
questions, and the README has to say so in one place:

| control | question | when it acts |
| --- | --- | --- |
| the project selection | which projects are *asked* | before the fetch |
| the `Projects` filter row | which of the loaded tasks' memberships to keep | after it |

The row earns its keep on tasks in several projects: with four projects
selected, `Projects: platform` reads "of everything I am looking at, the
platform work", and does it per tab, so one tab can narrow where another does
not. The selection cannot do that — it is one list, and narrowing it would
unload the tasks the other tab wants.

The row stays free text and stays uncompleted, for a reason that has changed:
not because a second control would fight the project pane, but because the
pane is now part of the same panel and the row is the *other* operation on the
same names. Its comment in `src/app/task.rs` is rewritten to say that.

## 11. What a set still does not carry

Unchanged, and the README's list keeps every item but one:

- the sort, the grouping, the completed filter, subtask visibility, the
  column cursor, the scroll offset — how you are reading the answer
- `o` (selected only) and `v` (the hidden group) — both are ways of looking at
  the project *list*, not statements about which projects are in play
- project **visibility**: `*` and `h` keep writing `[[project]]`, which is one
  record per project for the whole app, not per set. A star is a fact about a
  project; a selection is a fact about a question.

## 12. Implementation notes

- `src/config/mod.rs`: `NamedFilterSet` gains `projects: Option<Vec<String>>`
  with `skip_serializing_if = "Option::is_none"`, validated for blank entries
  and de-duplicated. No `header.version` bump, and nothing added to
  `migrate_v1` (§2.1).
- `src/app/project_list.rs` owns both translations, because it is the only
  module that knows `ProjectKind::AssignedToMe`:
  `selection_for_filter_set() -> Vec<String>` writing `me` first, and
  `apply_filter_set_selection(&[String])` resolving `me`, dropping unknown
  gids, pushing the selection history, and keeping the cursor. The second is
  `restore_selection` with the history pushed — the shared half should come out
  as one private helper rather than two near-copies.
- `src/app.rs`: `load_named_filter_set` applies the selection after it loads
  the panel; `stage_named_filter_set` compares the projects independently of
  the dirty flag (§7); `load_projects`'s one restore site learns the §9 rule;
  the sidebar prompt carries the mode it interrupted so `y`, `n`, and `esc`
  return to it.
- `src/ui/runtime.rs`: `filter_sets::split_sidebar` moves up to the top-pane
  dispatch, taking the minimum width of whichever pane is being drawn, and
  `render_filter_sets_pane` is called from there for both. `render_filter_pane`
  keeps the orphaned-prompt fallback; `render_project_pane` grows the same one,
  ahead of its search footer.
- `src/ui/filter_sets.rs`: `MIN_PROJECT_WIDTH`, `HEADER_LINES` 3 → 4 (so
  `window_rows` follows for free), the projects line, and the two conditional
  body lines in `confirm_view`.

## 13. Acceptance criteria

- `[[filter_set]]` round-trips a `projects` list
- ~~an entry with no `projects` key loads without touching the selection~~ —
  superseded: it loads to nothing selected, like `[]`
- `me` round-trips, resolves to the assigned-to-me row on load, and is written
  for whoever is logged in rather than as their gid
- a gid the workspace does not return is skipped on load and still on disk
  afterwards; changing the selection while that entry is bound is what removes
  it
- ~~a config written before this milestone loads unchanged, and the header
  stays at version 2~~ — superseded: versions 1 and 2 are both migrated to 3,
  and the selection they carried is moved rather than dropped
- `b` opens the sidebar in the project view, and the same sidebar is still open
  after `f` and `p`
- the sidebar gives way at a narrower width in the project view than in the
  filter view
- the pinned header shows the project count, and reads `no projects` at zero
- the project pane's border names the bound set, and names nothing when the
  panel is unnamed
- `1`-`9`, `<`, `>`, `w`, `y`, `n`, and `d` work from the project view, and
  every project-mode key keeps its existing meaning
- `w` and `d` prompts appear on the sidebar's border in the project view, and
  on the project pane's border when the sidebar has given way
- loading a set from the project view replaces the selection, starts the fetch,
  and leaves the keys in the project view
- loading with the task pane closed marks the table out of date instead of
  fetching
- `u` after a load restores the previous selection, and `ctrl-y` puts it back
- the discard confirmation names the projects the entry will select, for every
  entry — `selects no projects at all` when it names none
- a selection change while bound rewrites the entry, and a burst of selection
  keys costs one file write that also updates `[view]`
- `n` clears the selection and `u` restores it
- at startup a bound entry's `projects` is what restores, and the `scratch`
  entry is what restores an unnamed panel
- the `Projects` filter row still filters, still per tab, and still has no
  completion
- `*`, `h`, `v`, and `o` are unchanged and write nothing to a filter set
- tests cover the schema and its absent/empty split, the `me` translation, the
  unknown-gid rule, the two-view sidebar and its width floors, the project-mode
  keys, the load path including the fetch and the selection history, the
  write-through and its single write, the startup precedence rule, and the
  confirmation's wording
