# Milestone 13.5: Named filter sets

[← all milestones](../plan.md)

Goal:

- give the filter panel a name, so a filter you built once can be recalled by
  pressing a digit — and keeps itself up to date while you use it

## 1. The plan

[Milestone 13](13-filter-sets.md) made the panel hold several sets, ORed
together. What it did not do is let you keep one. Every set you build dies with
the session, and the ones worth having — "everything assigned to me that is
overdue", "the two sections we are shipping this month" — are exactly the ones
that take the longest to type.

### 1.1 What a name captures

A **named filter set** is the whole panel: every tab, each tab's fields, each
tab's negation, and each field's query, match mode, require-empty flag, and
negation. One name, one complete filter expression — including a union across
tabs, which is the thing the panel can express and a single tab cannot.

It is deliberately *not*:

- the sort, the grouping, the completed filter, or subtask visibility. Those are
  view state; the Gantt milestone already drew this line and nothing since has
  wanted it moved.
- the project selection. A saved filter is a question about tasks, and which
  projects it is asked of is the *other* half of the screen.
- the field cursor, the scroll offset, or which tab is active.

### 1.2 The sidebar

`b` toggles a `Sets` pane down the left-hand side of the filter view. It is a
pane of its own — its own border, its own title — and it is **never focused**:
`j` and `k` keep walking the filter fields, and the sidebar's thin, unfocused
border is what says so.

```
┌ Sets ──────────┐┏ Filters ━ any of │ 1● │ set 2● │ ━━━━━━━━━━━━━ 1 active ┓
│ ▸ Sprint triage││    Title     fuzzy     —                               ┃
│   2 sets · 3   ││    Assignee  fuzzy     alex                            ┃
│ ───────────────││▍ ● Due       date      (none)                          ┃
│ 1 Blocked      ││    Start     date      —                               ┃
│ 2 Overdue mine ││    State     labels    —                               ┃
│ 3 ▸Sprint triage   Projects  contains  —                                 ┃
│ 4 Waiting on   ││    Priority  labels    —                               ┃
└──────── 1-4 of 4┛━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┛
```

Top of the list, pinned above a rule, is **current**: the live panel, named if it
came from somewhere and `unnamed` if it did not, with how many sets and how many
active filters it holds. Below the rule are the saved entries in name order,
numbered from the top of the visible window, with the loaded one marked.

### 1.3 The keys

| key | what it does |
| --- | --- |
| `b` | toggle the sidebar |
| `1`–`9` | load the entry at that position in the visible window |
| `<` `>` | page the window, when there are more entries than fit |
| `w` | save the panel under a name |
| `y` | copy to new: keep what is on screen, stop being the named entry |
| `n` | start a completely fresh panel |
| `d` | delete the loaded entry |

All eight are configurable, like everything else.

### 1.4 Loading binds the panel to the name

Pressing a digit replaces the panel — every tab — with the named entry, and
**binds** the panel to it. From then on the entry is a live view rather than a
snapshot: type into a field, add a tab, negate a set, and the named entry
changes with it, on disk, in `tuisana.toml`.

This is the behaviour worth being explicit about, because the alternative — a
snapshot you have to remember to re-save — is the one that loses work. A named
set behaves like a file you have open, not like a clipboard.

Three escapes from it:

- `y` **copies the panel to a new unnamed one**. The panel keeps exactly what
  it is showing; `current` goes back to `unnamed`; the named entry keeps
  whatever was last written to it. This is how you take a saved filter as a
  starting point and then go somewhere else with it without disturbing the
  original. It is a detach, named for what it is *for*.
- `n` **starts from nothing**: one empty set, every row back to the match mode
  it was built with, nothing parked, and nothing bound. Stronger than the
  `cleared` that `a` uses, which keeps the match modes on purpose so a second
  set inherits the first one's — this is a blank slate. Like a load, it goes
  through the fetch decision, because dropping a `due` filter widens the
  window pushed down to Asana.
- `w` saves under a new name, which also rebinds to the new one.

The write itself happens once per settled burst of typing, not once per
keystroke — the same `input_pending` rule that already keeps a burst of typing
to one table rebuild (§2.5).

### 1.5 Saving and deleting

`w` opens a one-line prompt on the sidebar's bottom border, opening the sidebar
first if it was closed, pre-filled with the loaded name. `enter` commits, `esc`
cancels. A name that already exists is overwritten; a new one is created and
becomes the loaded entry. An empty or whitespace-only name is refused, with the
prompt left open.

`d` deletes the **loaded** entry, after a `y`/`n` confirmation on the same
prompt line, and detaches the panel. It is refused when nothing is loaded: with
no cursor in the sidebar there is no other unambiguous target, and "the one you
are currently editing" is a target the user just chose by pressing its number.

### 1.6 Persistence

Entries live in `tuisana.toml`, alongside the project visibility the app already
rewrites:

```toml
[[filter_set]]
name = "Sprint triage"

  [[filter_set.set]]

    [[filter_set.set.field]]
    key = "assignee"
    query = "alex"
    match = "fuzzy"

    [[filter_set.set.field]]
    key = "due"
    query = "..today"

  [[filter_set.set]]
  negated = true

    [[filter_set.set.field]]
    key = "custom:Priority"
    query = "Low"
```

Anything at its default is left out, so a simple entry stays short. The file is
writable by hand, and is read back exactly as written.

Three constraints carry over unchanged, and every one of them has a new way to
be violated here:

- **A rebuild happens after every project finishes loading**, and
  `restore_queries` is the only thing that carries user state across it. Every
  new field added in §2.3 has to be re-applied there.
- **The filter panel's rows are one line each.** The sidebar's rows must be too,
  so its window arithmetic stays a plain index.
- **The due date is pushed down to Asana**, and `TaskQuery::covers` records the
  window that was fetched as cached. Loading a named entry can widen the due
  window, so it has to go through the same fetch decision as any other filter
  change or the rows it needs are recorded as covered and never arrive (§2.5).

### 2.1 The saved model, in `src/config/mod.rs`

```rust
/// One named filter set: a whole filter panel, saved under a name.
#[derive(Clone, Debug, Deserialize, Serialize, PartialEq, Eq)]
pub struct NamedFilterSet {
    pub name: String,
    /// The ORed sets, in tab order.
    #[serde(default, rename = "set", skip_serializing_if = "Vec::is_empty")]
    pub sets: Vec<SavedFilterSet>,
}

/// One tab of a named filter set.
#[derive(Clone, Debug, Default, Deserialize, Serialize, PartialEq, Eq)]
pub struct SavedFilterSet {
    #[serde(default, skip_serializing_if = "is_false")]
    pub negated: bool,
    /// Only the fields that filter something; an untouched row is not written.
    #[serde(default, rename = "field", skip_serializing_if = "Vec::is_empty")]
    pub fields: Vec<SavedFilterField>,
}

/// One filter row's value, keyed the way the panel keys its rows.
#[derive(Clone, Debug, Deserialize, Serialize, PartialEq, Eq)]
pub struct SavedFilterField {
    /// `title`, `assignee`, `due`, `start`, `state`, `projects`, or
    /// `custom:<Name>` — `TaskFilterFieldSpec::key`, which is keyed by custom
    /// field *name* precisely so it survives a reload that brings different ids.
    pub key: String,
    #[serde(default, skip_serializing_if = "String::is_empty")]
    pub query: String,
    /// `fuzzy` | `contains` | `regex`. Omitted when it is the row's default.
    #[serde(default, rename = "match", skip_serializing_if = "Option::is_none")]
    pub string_mode: Option<String>,
    /// The row requires no value at all.
    #[serde(default, skip_serializing_if = "is_false")]
    pub empty: bool,
    #[serde(default, skip_serializing_if = "is_false")]
    pub negated: bool,
}
```

Hang it off `Config` the way `project_visibility` is hung:

```rust
#[serde(default, rename = "filter_set", skip_serializing_if = "Vec::is_empty")]
pub filter_sets: Vec<NamedFilterSet>,
```

…plus the arm in the hand-written `PartialEq` (line 43) and in `Default`.

**The scalar-before-table rule is load-bearing.** `toml`'s serializer cannot
emit a value after it has emitted a table, so in every struct above the scalars
come first and the `Vec` last. Getting this wrong does not fail a unit test that
only round-trips through `Value` — it fails at `save_to_source_path`, on a real
user's config. §4.2 is the test that catches it.

`validate()` gains: names must be non-empty after trimming; no two names may be
equal ignoring case (the sidebar lists them by number, and two rows reading the
same is a trap); `match`, when present, must be one of the three modes. Unknown
`key` values are *not* rejected — a `custom:Priority` from a project you have
not loaded this session is legitimate, and §2.2 is about keeping it.

### 2.2 Panel ↔ saved, in `src/app/task.rs`

Four conversions, next to `restore_from`, which is the existing code they all
resemble:

```rust
impl TaskFilterFieldState {
    /// This row as a saved field, or `None` when it filters nothing.
    fn to_saved(&self) -> Option<SavedFilterField> { … }
}

impl TaskFilterSet {
    fn to_saved(&self) -> SavedFilterSet { … }

    /// Writes a saved set's values onto a freshly built field list.
    ///
    /// The same matching rule as `restore_from`: by `spec.key`, with label rows
    /// deriving `label_values` from the query, `empty_required` gated on
    /// `spec.can_be_empty`, and the caret clamped to the new text.
    fn apply_saved(&mut self, saved: &SavedFilterSet) { … }
}

impl TaskFilterEditorState {
    fn to_saved(&self) -> Vec<SavedFilterSet> { … }

    /// Replaces every set with the saved ones, keeping the panel's own state
    /// (visibility, the field cursor) and clamping the active tab.
    fn apply_saved(&mut self, saved: &[SavedFilterSet]) { … }
}
```

**Unresolved fields.** A saved field whose `key` matches no row in the current
dataset — a custom field belonging to a project that is not loaded — must not be
dropped, because the panel is written back to disk and a dropped field is a
deleted filter. Give `TaskFilterSet` one more field:

```rust
/// Saved values with no row to land on yet.
///
/// A custom-field row only exists once a project carrying that field has
/// loaded, and the panel is written back to the named entry on every change —
/// so a value with nowhere to go has to be parked rather than discarded, or
/// loading a set with the wrong projects selected would quietly erase half of
/// it. Re-resolved on every rebuild, and written back out by `to_saved`.
unresolved: Vec<SavedFilterField>,
```

`apply_saved` parks what it cannot match, `to_saved` appends it back, and
`restore_from` carries it across the streaming rebuild and retries the match
each time — which is when it actually resolves, because that rebuild is exactly
the moment a new project's fields appear.

### 2.3 What the panel remembers

`TaskFilterEditorState` gains:

```rust
/// The named entry the panel currently *is*, if any.
///
/// Some(name) means every change writes through to that entry. `y` clears it,
/// which is the whole of "detach".
loaded: Option<String>,
/// Set by `refresh_table` whenever the panel is bound; cleared by a write.
dirty: bool,
sidebar_visible: bool,
/// First saved entry in the numbered window.
sidebar_page_start: usize,
prompt: Option<SidebarPrompt>,
```

```rust
/// The sidebar's one-line prompt.
enum SidebarPrompt {
    /// Typing a name for `w`.
    Save { text: String, caret: usize },
    /// Confirming `d`.
    ConfirmDelete { name: String },
}
```

**Do not mark `dirty` in twenty mutators.** Every panel mutation already ends in
`TaskState::refresh_table`; set it there, unconditionally, when `loaded` is
some. It will over-report — a rebuild triggered by data arriving marks the panel
dirty without the user having touched it — and that is fine, because the writer
in §2.5 compares before it writes and skips a no-op. One line, in the one place
nothing can bypass, beats correctness spread across every key handler.

`restore_queries` (line 502) must carry `loaded`, `dirty`, `sidebar_visible`,
`sidebar_page_start`, `prompt`, and — via `restore_from` — `unresolved`. This is
the rule from `developer.md`: state the user can change that is not re-applied
there vanishes mid-load.

### 2.4 Actions, modes, bindings

In `src/input/mod.rs` — enum, `from_command`, and `Display`, all three:

| variant | command | default key | mode |
| --- | --- | --- | --- |
| `FilterSetsToggle` | `filter_sets_toggle` | `b` | filter |
| `FilterSetLoad(u8)` | `filter_set_load_1` … `_9` | `1`–`9` | filter |
| `FilterSetsPageBack` | `filter_sets_page_back` | `<` | filter |
| `FilterSetsPageForward` | `filter_sets_page_forward` | `>` | filter |
| `FilterSetSave` | `filter_set_save` | `w` | filter |
| `FilterSetCopyToNew` | `filter_set_copy_to_new` | `y` | filter |
| `FilterSetNew` | `filter_set_new` | `n` | filter |
| `FilterSetDelete` | `filter_set_delete` | `d` | filter |

`FilterSetLoad` carries its position rather than becoming nine variants;
`from_command` parses the suffix and `Display` writes it back. `Action` already
derives `Clone, Debug, PartialEq, Eq, Hash`, so a `u8` payload costs nothing.

All nine digits are bound explicitly in `default_bindings()`. Verbose, but this
config is explicit everywhere else, and it means a user can rebind them. `0` is
left alone — it is `restore_top_pane` globally.

`<` and `>` are safe: the input layer lowercases letters, so shifted *letters*
are unreachable, but shifted punctuation arrives as its own character. `,` and
`.` are bound in task mode only, and `<`/`>` are unbound everywhere.

**A new mode, `Mode::FilterSetName`**, for the prompt:

- added to the `Mode` enum, `label()` (`"set name"`), and `Mode::allows_any_fallback`'s
  exclusion list, beside `ProjectSearch`, `FilterEdit`, and `Calendar` — so an
  unbound letter types instead of firing `b` or `d`.
- added to `focused_pane` (→ `Top`), `help_visible` (→ the task-side toggle), and
  `groups_for` in `src/ui/help_overlay.rs`.
- its keys are read outside the keymap, in `App::handle_filter_set_name_input`,
  modelled on `handle_project_search_input` (`src/app.rs:460`): `enter` commits,
  `esc` cancels, `backspace` deletes, an unmodified char types. When the prompt
  is `ConfirmDelete`, the same handler reads `y` / `n` / `esc` instead.

One mode covers both prompts. The status bar and the help overlay each gain one
entry rather than two, and the handler already has the prompt in hand to know
which it is.

### 2.5 App wiring, in `src/app.rs`

`FilterSetsToggle`, the paging pair, and the prompt-opening half of `w` and `d`
are pure panel state: handle them in `TaskState::apply_action`, beside
`Action::FilterSetAdd` (line 2672).

Load, save-commit, delete-commit, and detach need `&mut self.config`, so they
belong in `App::handle_action`. **They must not `return Ok(None)` early.**
Loading a named entry can widen the due window pushed down to Asana, and
`TaskQuery::covers` records a fetched window as cached — so a load that skips
`update_task_data_after_action` leaves rows permanently missing rather than
merely late. Either fall through to the tail of `handle_action`, or call
`update_task_data_after_action(task_targets_before)` explicitly before
returning. §4.5 is the test.

The write-through needs exactly one place that runs after every key, including
the ones handled outside the keymap:

```rust
pub fn handle_key_event(&mut self, keymap, event, page_size) -> Result<Option<AppCommand>> {
    let result = self.handle_key_event_inner(keymap, event, page_size);
    // The last key of a burst is the one with an empty queue behind it, which
    // is the same moment `settle_table` picks to rebuild. Typing a filter is
    // one write, not one per character.
    if !self.tasks.input_pending() {
        self.sync_named_filter_set();
    }
    result
}
```

`sync_named_filter_set` returns nothing and never fails upward:

```rust
/// Writes the panel back to the named entry it was loaded from.
///
/// No-op unless the panel is bound and something changed. The comparison is
/// what makes §2.3's deliberately over-eager `dirty` flag safe.
///
/// A failure here is reported and dropped rather than returned. Project
/// visibility can afford to propagate a write error because it happens on one
/// deliberate keypress; this runs while someone is typing into a filter, and an
/// unwritable config must not take the session down mid-word.
fn sync_named_filter_set(&mut self) { … }
```

Clear `dirty` whether the write succeeded or failed, so a broken config file
produces one message rather than one per keystroke.

## 3. The tests that matter

1. **Round trip.** Panel → saved → TOML → parsed → applied gives back an
   identical panel, across all four field kinds, a negated set, and a
   require-empty.
2. **The file the app writes is readable.** Serialize a config holding two
   named entries and parse it back. This is the scalar-before-table hazard, and
   nothing else catches it.
3. **Loading replaces the whole panel** — tab count, negations, and values — and
   clamps the field cursor and active tab.
4. **An unresolved field survives.** Load an entry naming a custom field that is
   not in the dataset, change something else, let it write back: the unmatched
   field is still in the file. Then load the project that has it and confirm the
   row picks the value up.
5. **A load that widens the due window starts a fetch**, rather than filtering
   the cache and recording the window as covered.
6. **Everything survives a streaming reload**: the loaded name, the binding, the
   sidebar page, and the unresolved fields, across `restore_queries`.
7. **Write-through is once per settled burst.** Nothing is written while
   `input_pending`; the key that empties the queue writes once.
8. **A no-op change writes nothing**, so the over-eager `dirty` flag cannot
   churn the config file.
9. **Copy-to-new stops the write-through** and leaves the saved entry as it
   was; **`n` does the same and keeps nothing at all**, including the match
   modes, the extra tabs, and the parked fields.
10. **Save** binds under a new name, overwrites an existing one, and refuses an
    empty one with the prompt still open.
11. **Delete** removes the entry, detaches the panel, requires confirmation, and
    is refused with nothing loaded.
12. **Digits address the visible window**, and `<`/`>` change what they address;
    paging clamps at both ends and is a no-op when everything fits.
13. **The sidebar is dropped, not squeezed**, below the minimum panel width.
14. **The eight commands parse, round-trip through `Display`, and are bound**,
    and the hint bar and help overlay list them.
15. **End to end, driven by keys**, plus snapshots at 80/120/200.

## 4. How to write them

### 4.1 Round trip — `src/app/task.rs`, `mod tests`

Build a panel from the shared fixture, fill in one field of each kind, negate a
row and a set, add a second set, `to_saved()`, serialize, parse, `apply_saved()`
onto a panel built fresh from the same dataset, and assert the two
`TaskFilterEditorState::sets` are equal. Asserting on the whole `Vec<TaskFilterSet>`
rather than field by field is what makes the test catch a field added later and
not carried.

### 4.2 The file is readable — `src/config/mod.rs`, `mod tests`

```rust
#[test]
fn a_config_holding_named_filter_sets_round_trips_through_the_serializer() {
    // The `toml` serializer cannot emit a value after a table, so a struct with
    // its `Vec` before its scalars serializes to something it cannot read back
    // — and only at `save_to_source_path`, on a real config.
    let config = config_with_two_named_sets();
    let text = toml::to_string_pretty(&config).expect("serializes");
    assert_eq!(Config::from_toml_str(&text).expect("parses"), config);
}
```

Pair it with a literal-TOML test that parses the block from §1.6 verbatim, so
the documented shape and the serialized shape are both pinned.

### 4.3 Unresolved fields — `src/app/task.rs`, `mod tests`

Apply a saved entry naming `custom:Priority` to a panel built from a dataset
with no such field; assert `to_saved()` still contains it. Then rebuild the
editor from a dataset that *does* have it, run `restore_queries`, and assert the
row now carries the value and `unresolved` is empty. Both halves matter: the
first is the data-loss guard, the second is the payoff.

### 4.4 Write-through and the burst rule — `src/app.rs`, `mod tests`

Use the `config_with_source_path` fixture already there for the gantt-colour
test (`src/app.rs:1369`). Load a named entry, then:

```rust
app.tasks.set_input_pending(true);
for ch in "alex".chars() { app.handle_key_event(&keymap, key(ch), 10)?; }
assert_eq!(reread(&path).filter_sets[0], before, "nothing written mid-burst");

app.tasks.set_input_pending(false);
app.handle_key_event(&keymap, key('x'), 10)?;
assert_eq!(reread(&path).filter_sets[0].sets[0].fields[0].query, "alexx");
```

Then the no-op case: a key that changes nothing (`j`, moving the field cursor)
leaves the file's modification time alone.

### 4.5 A load that needs a fetch — `src/app.rs`, `mod tests`

The Milestone 13 §2.5 hazard, one level up. Load tasks with no due filter, save
that as an entry, then load a *second* entry whose due row reads `2027-01`.
Assert a fetch was started — `task_data_receiver.is_some()` — rather than the
table being rebuilt from cache. `FakeAsanaClient` records the queries it was
given, so also assert the `due_after`/`due_before` that went out.

### 4.6 The sidebar — `src/ui/filter_sets.rs`, `mod tests`

Number the rows from the window start, not from the entry index: with

### 4.7 Commands and bindings — `src/config/mod.rs` and `src/input/mod.rs`

Extend `default_bindings_include_filter_controls` (`src/config/mod.rs:972`) with

### 4.8 End to end — `tests/task_view_integration.rs`

`f` opens the panel, `j` `enter` `alex` `enter` fills Assignee, `w` opens the
prompt, `mine` `enter` saves and binds. Then `j` `e` requires an empty Due and
the entry on disk has both. `y` copies to a new unnamed panel; another edit
leaves the file alone. `1` loads it back and the Due row is required-empty
again, and `n` then leaves the panel empty and the file untouched.

## Deferred, deliberately

- **Renaming and reordering entries.** Both are config-file edits today, and the
  sidebar has no cursor to hang them off.
- **A cursor in the sidebar.** The digits are the access path on purpose; a
  focusable list is a mode, and a mode is worth adding only once something needs
  more than "load this one".
- **Saving the project selection with the filter.** Tempting — "my sprint" is a
  filter *and* a set of projects — but it makes loading an entry reach across
  the screen and start a different fetch. Worth its own milestone if it is worth
  anything.
- **Saving sort, grouping, or the completed filter.** View state, on the same
  side of the line the Gantt chart drew.
- **Load-by-name with completion**, and sharing entries between machines.

## Definition of done

- a filter panel of any shape can be saved under a name, and loaded back with
  one keypress; `n` starts a fresh one from nothing
- a loaded entry stays current as it is edited, without a save step, and one
  burst of typing costs one write
- `y` copies to a new unnamed panel and `d` deletes, and neither can silently
  lose a filter that belongs to a project that is not loaded
- the sidebar shows the live panel and the saved entries, never takes focus, and
  gives way rather than squeezing the filter rows on a narrow terminal
- loading an entry that needs data the cache does not hold fetches it
- a config write that fails reports itself instead of ending the session
- all eight keys are configurable, and the hint bar and help overlay list them
- tests cover the round trip, the serializer, unresolved fields, the burst rule,
  the fetch decision, the sidebar's window arithmetic, and an end-to-end
  key-driven save/copy-to-new/load, plus snapshots at 80/120/200
